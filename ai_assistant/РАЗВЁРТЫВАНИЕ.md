# Развёртывание прототипа UL-17568 на телефонной станции

Инструкция для того, кто пойдёт непосредственно на станцию Астериска и будет
делать живой тестовый звонок. Предполагается, что вы знаете свою
инфраструктуру (где `extensions.conf`, как перечитать диалплан, как открыть
порт в брандмауэре), но не помните внутренностей этого прототипа — они здесь
расписаны.

Сервис (виртуалка с распознаванием и синтезом) — `10.20.0.10`.
Порты сервиса (см. `ai_assistant/service/config.py`): **8080** — HTTP
(`/health`, `/dialog`, `/tts`, `/metrics`), **50051** — gRPC (поток
распознавания).

## 1. Скопировать файлы на станцию

Четыре рабочих файла AGI-клиента и один звуковой файл на случай отказа сервиса:

```bash
scp ai_assistant/agi/ai_assistant.py ai_assistant/agi/ai_assistant_last_will.py \
    root@<астериск>:/var/lib/asterisk/agi-bin/
scp ai_assistant/proto/speech_pb2.py ai_assistant/proto/speech_pb2_grpc.py \
    root@<астериск>:/var/lib/asterisk/agi-bin/
scp ai_assistant/sounds/service_unavailable.wav \
    root@<астериск>:/var/lib/asterisk/sounds/ai_bot/service_unavailable.wav
```

`ai_assistant_last_will.py` — скрипт последней воли: Астериск запускает его
отдельным процессом на `exten => h`, когда канал уже разорван, и он сообщает
в ERP, что клиент положил трубку (обращение уходит в ПЦК). Отдельным
скриптом это сделано не для красоты: основной `ai_assistant.py` при обрыве
канала умирает мгновенно (`SIGHUP` переведён на `SIG_DFL` — намеренно, против
зомби-процессов, которые роняли станцию), сказать об обрыве он поэтому не
может физически. Всё, что нужно последней воле, основной скрипт заранее
кладёт в переменные канала: `documentId`, `ScriptFinished`,
`LastRecognizedText`. Ни grpc, ни заглушек protobuf этот скрипт не требует —
он самодостаточен и поднимется, даже если основной не поднимается.

`service_unavailable.wav` — заранее записанная фраза «Минуту, перевожу ваш
звонок на специалиста». Скрипт AGI играет её, если речевой сервис недобежал
или упал целиком (обрыв `/dialog` или обрыв gRPC-потока) — тогда синтезировать
уже нечего, сервис же и лежит. Путь на станции жёстко зашит в скрипте
константой `SERVICE_UNAVAILABLE_SOUND`, менять имя файла нельзя.

## 2. Проверить, что скрипт запускается под Python 3.9 на станции

На станции:

```bash
python3 --version
python3 -m py_compile /var/lib/asterisk/agi-bin/ai_assistant.py
python3 -m py_compile /var/lib/asterisk/agi-bin/ai_assistant_last_will.py
```

Первая команда должна показать `Python 3.9.x` — скрипт написан специально под
эту версию (в шапке файла есть предупреждение: синтаксис 3.10+ не
использовать). Вторая команда ничего не выведет при успехе — это и есть
проверка, что скрипт **компилируется** тем же интерпретатором, под которым
будет реально исполняться. Если `py_compile` ругается на синтаксис — не
продолжать, это баг, а не особенность станции.

**`py_compile` не ловит проблемы импорта — нужна отдельная, настоящая
проверка.** Компиляция байткода не выполняет ни одной строки модуля, а
`ai_assistant.py` тянет за собой сгенерированные заглушки gRPC
(`speech_pb2.py`, `speech_pb2_grpc.py`), которые собраны новым инструментом:
`speech_pb2.py` на импорте зовёт `ValidateProtobufRuntimeVersion` —
функцию, которой нет в старых сборках `protobuf`; `speech_pb2_grpc.py` сам
явно бросает `RuntimeError`, если версия `grpcio` старее той, которой
сгенерирован файл. На станции Python 3.9.2 и pip 20.3.4, библиотеки стоят
годами — есть высокая вероятность, что скрипт **не импортируется вообще**:
абонент услышит тишину и отбой, без всякого запасного пути (аварийный
`failover_to_support()` внутри скрипта тут не спасёт — сам процесс не
запустится). Проверить это одной командой:

```bash
python3 -c "
import sys
sys.path.insert(0, '/var/lib/asterisk/agi-bin')
import grpc
import requests
import asterisk.agi
import func_timeout
import speech_pb2
import speech_pb2_grpc
import google.protobuf
print('grpc:', grpc.__version__)
print('protobuf:', google.protobuf.__version__)
print('IMPORT OK')
"
```

Ожидается три строки и `IMPORT OK` в конце. Модули `grpc`, `requests`,
`asterisk.agi` (pyst2), `func_timeout` на станции должны быть уже установлены
с прошлой задачи (Task 10, тонкий AGI-клиент). Если раньше AGI-скрипты на
этой станции не разворачивались — доустановить их под `python3` (тем же
интерпретатором, что показала первая команда) до звонка.

**Уже сделано 13.08.2026.** На станции `asterisk-ai` оказались `grpcio 1.51.1` и
`protobuf 4.21.12`, и первая же проверка упала с
`ImportError: cannot import name 'runtime_version' from 'google.protobuf'`.
Заглушки в `ai_assistant/proto/` **пересобраны генератором `grpcio-tools==1.62.3`**
(он тянет `protobuf 4.25`, то есть ещё до появления `runtime_version`) и
проверены с обеих сторон: импортируются и под старым набором станции, и под
новым набором сервиса (`grpcio 1.68.1` / `protobuf 5.29.1`), все 130 тестов
зелёные. Более старый `grpcio-tools==1.51.1` под Python 3.12 не собирается —
готовых сборок для этой версии питона не существует, поэтому взят ближайший
подходящий.

Если заглушки понадобится собрать заново — брать версию генератора **не старше
1.62.x**: начиная с 1.64 в сгенерированный код добавляется обращение к
`runtime_version`, которого на станции нет.

**Если команда упала** (`AttributeError` на `ValidateProtobufRuntimeVersion`,
`RuntimeError` про несовпадение версий `grpcio`, или любой другой
`ImportError`/`ModuleNotFoundError` на `speech_pb2`/`speech_pb2_grpc`) — дело
в том, что заглушки сгенерированы более новым `grpcio-tools`, чем то, что
реально стоит на станции. Не пытаться понижать версии на самой станции
(там древний pip 20.3.4, и трогать боевой набор пакетов лишний раз не
хочется) — вместо этого перегенерировать заглушки на машине сервиса той же
версией пакета генерации, что стоит на станции, и перезалить оба файла:

Четыре шага, и каждый — на своей машине и в своей оболочке. Не копировать
блок целиком одной командой: шаг 1 — на станции (bash), шаг 2 — на машине
сервиса (PowerShell, Windows), шаги 3-4 — снова на станции (bash).

**Шаг 1 — на станции, bash.** Узнать версии, под которые нужно генерировать
заглушки (если `import speech_pb2`/`speech_pb2_grpc` падает раньше, чем
успевает напечатать версии из команды выше, — смотреть версии до них:
`import grpc` и `import google.protobuf` сами по себе обычно проходят,
падает именно следующий импорт сгенерированных файлов):

```bash
python3 -c "import grpc; print(grpc.__version__)"
python3 -c "import google.protobuf; print(google.protobuf.__version__)"
```

**Шаг 2 — на машине сервиса (10.20.0.10, Windows), PowerShell.**
Изолированный venv с генератором ровно тех версий, что показала станция на
шаге 1 (не той версии, что стоит в `service/` самого сервиса — сервис и
станция намеренно живут на разных версиях библиотек, это и есть причина
проблемы):

```powershell

& $env:TEMP\protogen\Scripts\pip install "grpcio-tools==<ВЕРСИЯ_GRPCIO_СО_СТАНЦИИ>" "protobuf==<ВЕРСИЯ_PROTOBUF_СО_СТАНЦИИ>"
& $env:TEMP\protogen\Scripts\python -m grpc_tools.protoc -I ai_assistant\proto --python_out=ai_assistant\proto --grpc_python_out=ai_assistant\proto ai_assistant\proto\speech.proto
```

**Шаг 3 — с машины сервиса на станцию, bash** (та же команда, что и в шаге 1
раздела "Скопировать файлы на станцию" выше):

```bash
scp ai_assistant/proto/speech_pb2.py ai_assistant/proto/speech_pb2_grpc.py \
    root@<астериск>:/var/lib/asterisk/agi-bin/
```

**Шаг 4 — на станции, bash.** Повторить команду проверки импорта выше — до
`IMPORT OK` не продолжать.

Если для версии `grpcio` со станции вообще не существует пакета
`grpcio-tools` той же версии (совсем древняя связка) — взять ближайшую более
раннюю версию `grpcio-tools`, которая всё ещё существует в PyPI, и повторить
проверку импорта: цель не идеальное совпадение версий, а чтобы
сгенерированный файл не звал функции, которых на станции нет.

## 2а. Переключатель реального перевода звонков (REAL_REDIRECT)

В `ai_assistant/agi/ai_assistant.py` есть константа модуля `REAL_REDIRECT`,
сейчас `False`. Пока она выключена, вместо команды перехода `Goto` на другой
отдел (и при обычном решении диалога, и при аварийном переводе на
сопровождение при отказе сервиса) скрипт пишет в лог станции заметную строку
`REDIRECT (dry-run, ...)` / `FAILOVER (dry-run, ...)` с тем, куда бы перевёл
звонок, и сам корректно завершает разговор (`hangup`). Это сделано намеренно
— спецификация прямо требует не дёргать живых операторов, пока идёт отладка
на тестовом номере: иначе отделы продаж и сопровождения получат поток
тестовых звонков.

**Включать `REAL_REDIRECT = True` можно только после того, как** сняты
успешные замеры задержки/качества/нагрузки по разделу 8 этой инструкции **и**
смены поддержки/продаж предупреждены, что на их номера могут начать приходить
переводы из тестового прототипа. После правки константы — заново скопировать
файл на станцию (шаг 1 выше), одной правки цифры в диалплане недостаточно.

## 2б. Переключатель обращений в ERP (ERP_INTEGRATION)

Рядом с `REAL_REDIRECT` в `ai_assistant/agi/ai_assistant.py` лежит константа
`ERP_INTEGRATION`, сейчас `True`. Это выключатель всей интеграции с ERP: пока
он включён, скрипт на каждом звонке заводит обращение (`AiAssistantCallStart`),
сообщает тему разговора (`AiAssistantEquipment`) и перевод
(`AiAssistantTransfer`). Выключив его, можно отлаживать сам разговор, не
засоряя базу обращениями от проб — но тогда не будет ни обращений, ни истории,
ни ухода в ПЦК при обрыве.

Ни один вызов ERP не имеет права задержать или уронить разговор: таймаут
пять секунд, любое исключение уходит в лог станции строкой `ERP ERROR ...`,
и звонок продолжается как ни в чём не бывало. Клиент в трубке важнее
обращения.

Обращение создаётся **в момент приёма звонка**, а не при переводе на
оператора: трубку бросают и на первой секунде, а чтобы обращение ушло в ПЦК
при обрыве, к этому моменту оно должно существовать.

## 5. Заменить блок `74951468847` в диалплане

В `/etc/asterisk/extensions.conf` найти текущий блок extension
`74951468847` и заменить его целиком на:

```
exten => 74951468847,1,Answer
same => n,Set(CDR(userfield)=aitest)
same => n,Set(MIXMONITOR_FILENAME=/var/spool/asterisk/monitor/${UNIQUEID})
same => n,MixMonitor(${MIXMONITOR_FILENAME}.wav49,W(4))
same => n,Verbose(======== BOT AI PROTOTYPE === с номера: ${CALLERID(num)})
same => n,Set(SpeechServiceHost=10.20.0.10)
same => n,Set(Aster2ServiceAddress=10.20.0.15:65/Aster2ServiceWebHttp)
same => n,Set(AGIEXITONHANGUP=no)
same => n,EAGI(ai_assistant.py,120)
same => n,Verbose(======== BOT AI PROTOTYPE FINISHED ========)
same => n,Hangup()

exten => h,1,AGI(ai_assistant_last_will.py)
```

Разбор нетривиальных строк:

- `MixMonitor(...)` — запись разговора, файл ляжет в
  `/var/spool/asterisk/monitor/<UNIQUEID>.wav49`.
- `Set(SpeechServiceHost=10.20.0.10)` — адрес сервиса. Порты HTTP/gRPC
  скрипт берёт из своих значений по умолчанию (`8080`/`50051`, совпадают с
  портами сервиса из раздела выше) через переменные `SpeechServiceHttpPort` /
  `SpeechServiceGrpcPort` — их в диалплане можно не задавать, если порты не
  менялись. Если поменяли порты сервиса — добавить сюда ещё две строки
  `Set(SpeechServiceHttpPort=...)` / `Set(SpeechServiceGrpcPort=...)`.
- `Set(Aster2ServiceAddress=...)` — адрес службы Aster2Service, через которую
  оба скрипта ходят в ERP заводить обращение. Значение то же самое, что уже
  выставляется в диалплане для боевого бота (`recosintsite_V2.py`), и оно же
  зашито в скрипты значением по умолчанию — строку можно не добавлять, если
  служба не переезжала. **Если в этом контексте переменная уже выставляется
  выше по диалплану, второй раз её задавать не надо.**
- `exten => h,1,AGI(ai_assistant_last_will.py)` — скрипт последней воли.
  Астериск исполняет расширение `h` при разрыве канала, то есть когда клиент
  положил трубку. Именно этот вызов сообщает ERP об обрыве, и без него
  обращение не уйдёт в ПЦК: основной скрипт при обрыве умирает мгновенно и
  сказать ничего не успевает (см. `AGIEXITONHANGUP` ниже). Обратите внимание
  на `AGI`, а не `EAGI`: аудиопоток последней воле не нужен. Расширение `h`
  общее на весь контекст — если оно в контексте уже есть, добавить строку
  `same => n,AGI(ai_assistant_last_will.py)` к существующему, а не заводить
  второе. Скрипт сам отличает брошенную трубку от нормального конца
  разговора по переменной `ScriptFinished` и во втором случае в ERP не идёт —
  иначе каждый переведённый на оператора звонок попадал бы ещё и в ПЦК.
- **`Set(AGIEXITONHANGUP=no)` — обязательная строка, не пропускать.** Со
  значением `yes` обрыв EAGI при обрыве звонка оставляет дочерний процесс без
  `waitpid`, зомби-процессы копятся и в итоге роняют Астериск целиком —
  на этой станции уже так падало.
- `EAGI(ai_assistant.py,120)` — **число `120` здесь не предел длительности
  звонка**, хотя выглядит именно так. Скрипт `ai_assistant.py` не читает свои
  аргументы (`sys.argv` в нём нигде не используется) — это число просто
  игнорируется. Реальный предел одного звонка задан внутри самого скрипта
  константой `CALL_TIMEOUT_S = 120` (в начале `ai_assistant/agi/ai_assistant.py`)
  — их совпадение случайное. Если понадобится изменить лимит звонка, менять
  нужно именно эту константу в скрипте и заново копировать файл на станцию
  (шаг 1) — правка одной только цифры в диалплане ничего не даст.

Применить без перезапуска станции:

```bash
asterisk -rx "dialplan reload"
asterisk -rx "dialplan show 74951468847@pstn-in"
```

Во втором выводе должны быть видны строки `MixMonitor` и
`EAGI(ai_assistant.py,120)` — это подтверждает, что диалплан подхватился. Если
их нет — правка не применилась (опечатка в контексте `pstn-in` или в номере),
искать ошибку в выводе `dialplan reload` и не звонить, пока не увидите обе
строки.

Отдельно проверить, что подхватилось расширение `h` — оно живёт в контексте, а
не в номере, и в выводе выше его не видно:

```bash
asterisk -rx "dialplan show h@pstn-in"
```

Ожидается строка `AGI(ai_assistant_last_will.py)`. Если её нет, обрывы звонков
до ERP доходить не будут: обращение так и останется в подтипе бота вместо ПЦК.

## 6. Проверить сетевую доступность сервиса со станции

```bash
curl -s -m 5 http://10.20.0.10:8080/health && echo OK
nc -zv 10.20.0.10 50051
ping -c 4 10.20.0.10
```

Ожидается: `health` отвечает `{"status":"ok"}` и печатает `OK`, порт `50051`
открыт (`nc` пишет `succeeded` или аналог), `ping` — в пределах пары мс
(машины в одной локальной сети).

Если `health` не отвечает или порт закрыт — на машине сервиса
(`10.20.0.10`, Windows) открыть порты в брандмауэре:

```powershell
New-NetFirewallRule -DisplayName "AIA speech HTTP" -Direction Inbound -LocalPort 8080 -Protocol TCP -Action Allow
New-NetFirewallRule -DisplayName "AIA speech gRPC" -Direction Inbound -LocalPort 50051 -Protocol TCP -Action Allow
```

После этого повторить проверку с шага 6 со станции.

Заодно проверить доступность службы Aster2Service — через неё оба AGI-скрипта
ходят в ERP заводить обращение:

```bash
curl -s -o /dev/null -w "%{http_code}\n" -m 5 \
  http://10.20.0.15:65/Aster2ServiceWebHttp/ReturnConversationIntermediateResult3
```

Любой ответ, кроме таймаута и `000`, означает, что служба на месте (без тела
запроса она честно ругается — это нормально). Если ответа нет, звонок всё
равно состоится, но обращения в ERP не будет: в логе станции появится
`ERP ERROR ...`, и это единственное последствие.

## 7. Звонок

В одном окне на станции держать живой лог:

```bash
asterisk -rvvv
```

Позвонить с телефона на `74951468847`.

Ожидаемый ход разговора:

1. Бот здоровается («Здравствуйте, чем могу помочь?»).
2. Сказать: «стиральная машина не отжимает».
3. Бот переспрашивает (уточняющий вопрос по базе знаний).
4. Сказать: «да».
5. Бот сообщает о переводе звонка и кладёт трубку / переводит на
   сопровождение.

В консоли `asterisk -rvvv` смотреть на строки:

- `=== AI ASSISTANT START <uniqueid> ===` — скрипт запустился;
- `ERP: обращение <код> создано` — обращение в ERP заведено, дальше скрипт
  ходит туда уже с этим кодом. Строка `ERP: обращение не создано (...)` —
  повод открыть обращение по этому номеру руками и разобраться: чаще всего
  на телефоне линии не стоит галочка «Виртуальный AI помощник», без неё
  обработчик отказывается создавать обращение;
- `FINAL: <текст>` — что именно распознал движок на каждой реплике, это и
  есть материал для колонки «Распознано» в `RESULTS.md`;
- `REDIRECT -> 500` (или другой номер) — бот довёл диалог до перевода;
- `=== AI ASSISTANT LAST WILL <uniqueid> ... ===` — сработал скрипт последней
  воли. Появляется на каждом завершении звонка; если трубку бросили до
  перевода, обращение при этом уходит в ПЦК.

Проверить в ERP: обращение создано в подтипе «АстерБот AI: Новое обращение»,
в истории есть запись с вопросом клиента и проставленным типом оборудования, а
если положить трубку не дожидаясь перевода — подтип сменился на «Перезвонить
целевому клиенту».

Если бот молчит — по порядку проверить:

1. Сервис поднят и отвечает `/health` (раздел 0).
2. Файлы AGI на месте и владелец `asterisk` — на станции:
   `ls -la /var/lib/asterisk/agi-bin/` и
   `ls -la /var/lib/asterisk/sounds/ai_bot/cache/` (сюда должны появляться
   `.wav` по ходу разговора, тоже с владельцем `asterisk`).
3. Если вместо диалога бот сразу проигрывает «Минуту, перевожу ваш звонок на
   специалиста» и переводит на `489` — это аварийный переход
   (`failover_to_support` в скрипте), значит сервис не отвечал в момент
   звонка. Смотреть лог сервиса на `10.20.0.10`.

## 8. Снять замеры после звонка

С любой машины, у которой есть доступ к сервису:

```bash
curl -s http://10.20.0.10:8080/metrics | python -m json.tool
```

Вернёт тайминги по каждой распознанной реплике, но не все три отрезка сразу
— технически возможны только два, и по разным причинам:

- **`speech_end→stt_done` и `stt_done→dialog_done`** — оба в одном и том же
  объекте `/metrics`: сервис сам находит таймлайн звонка по `linkedId` (он
  же `session_id` в gRPC-потоке) и дописывает в него момент, когда диалоговая
  логика приняла решение.
- **`dialog_done→tts_done` в `/metrics` нет и не будет** — ручка `/tts` не
  получает `linkedId` (контракт с AGI-скриптом намеренно не менялся, см.
  "Обязательные ограничения" в постановке задачи), поэтому сопоставить
  конкретный синтез с конкретным звонком на стороне сервиса нечем. Вместо
  этого сервис пишет длительность каждого синтеза отдельной строкой в свой
  лог (`TTS <мс> ms | voice=... | text=...`) — это годится для общей
  статистики по движку синтеза, но не для привязки к одному звонку.

Отрезок `dialog_done→tts_done` (и `tts_done→playback_start`) для конкретного
звонка собирается из **лога станции**: `ai_assistant.py` пишет туда метки
`TIMING download_start`/`TIMING download_done` (вокруг скачивания
синтезированного WAV с сервиса) и `TIMING playback_start` (перед командой
`Playback`/`background`) с точностью до миллисекунды. Соединить с записью из
`/metrics` того же звонка можно по `linkedId` (это же `agi_uniqueid`,
виден в начале лога строкой `=== AI ASSISTANT START <uniqueid> ===`).

**Важно: `TIMING download_start`/`TIMING download_done` пишутся только при
промахе кэша станции.** `fetch_audio()` в `ai_assistant.py` проверяет
`AUDIO_CACHE_DIR` в первую очередь и при попадании отдаёт файл сразу, без
единого запроса к `/tts` — метки скачивания в этом случае в лог не попадают
вообще (отрезок `dialog_done→tts_done` для такой реплики можно считать
нулевым, но замерить его нечем). Типовые фразы (приветствие, уточняющие
вопросы по базе знаний) после первого же звонка на станции уже
закэшированы, и на втором и последующих звонках этот отрезок в логе не
появится. Для полного замера задержки (со всеми отрезками, а не только для
первого произнесения каждой фразы) перед звонком, по которому снимаются
цифры для `RESULTS.md`, — очистить кэш станции:

```bash
rm -f /var/lib/asterisk/sounds/ai_bot/cache/*.wav
```

(та же команда, что и в разделе 8а про смену голоса).

Перенести собранные тайминги в таблицу задержек в `ai_assistant/RESULTS.md`.

Параллельно во время самого звонка на виртуалке сервиса снять нагрузку —
на Windows проще всего диспетчером задач или:

```powershell
Get-Process python | Select-Object Id, @{N='MemMB';E={[math]::Round($_.WorkingSet64/1MB,1)}}, CPU
```

Записать в раздел «Нагрузка» `RESULTS.md`. Запись самого разговора —
`/var/spool/asterisk/monitor/<uniqueid>.wav49` — переслушать, чтобы заполнить
таблицу качества распознавания (что сказано / что реально распознано / ушло
ли в верную ветку диалога).

Затем повторить звонок теми же фразами со вторым движком: остановить сервис,
поднять заново с `AIA_STT_ENGINE=gigaam`, дождаться готовности (около 34
секунд, см. таблицу замеров в разделе 0), позвонить, снять те же цифры.

## 8а. Смена голоса синтеза — обязательно чистить кэш на станции

Имя файла в кэше на станции (`fetch_audio` в `ai_assistant.py`,
`FileToPlayback` из ответа `/dialog`) считается только от текста фразы.
На сервисе же кэш синтеза (`TtsCache._path_for` в `service/tts.py`) считается
от голоса **и** текста вместе. Из-за этого при смене голоса (`AIA_TTS_VOICE`
или параметр `voice_name`) сервис честно посчитает новый файл под новым
именем, а станция, у которой в кэше уже лежит файл со старым именем
(посчитанным только от текста), даже не обратится за новым — `fetch_audio`
видит, что файл по этому имени уже есть, и отдаёт его как есть. Результат:
станция продолжает играть старые WAV со старым голосом, пока её собственный
кэш не почистить руками.

После любой смены голоса — обязательно очистить каталог кэша на станции:

```bash
rm -f /var/lib/asterisk/sounds/ai_bot/cache/*.wav
```

(права `asterisk:asterisk` на сам каталог трогать не нужно — `mkdir`
из шага 3 их уже выставил, `rm -f` их не меняет).

## 9. Как вернуть всё назад

Если что-то пошло не так, или прототип решено выключить после обкатки —
вернуть extension `74951468847` к исходному состоянию (проигрывание
`ai_bot/labubu`), используя резервную копию из шага 4:

```bash
cp /etc/asterisk/extensions.conf.bak-<метка> /etc/asterisk/extensions.conf
asterisk -rx "dialplan reload"
asterisk -rx "dialplan show 74951468847@pstn-in"
```

`<метка>` — дата и время из имени файла, которое вывела команда `ls` в
шаге 4. Во втором выводе `dialplan show` не должно быть больше ни
`MixMonitor`, ни `EAGI(ai_assistant.py,120)` — значит откат применился.

Если прототип, наоборот, решено оставить включённым для дальнейшей обкатки —
этот шаг пропустить.
