# Станция Asterisk: выкладка, диалплан, разбор звонка

Для того, кто идёт на станцию `asterisk-ai` (10.20.0.11). Сокращено 12.11.2026 с 814 строк до действующего:
пошаговая первая установка августа и запуск на Vosk убраны, полный текст есть в истории git. Запуск самого
сервиса описан в `ai_assistant/README.md`.

Сервис: `10.20.0.10`, порты **8080** (HTTP: `/health`, `/dialog`, `/tts`, `/metrics`, `/knowledge`) и
**50051** (gRPC, поток распознавания).

Блок диалплана ниже записан по журналу правки 09.11.2026, со станцией при сокращении не сверялся. Перед
правкой смотреть живой файл.

## 1. Что лежит на станции

| Файл | Куда | Зачем |
|---|---|---|
| `agi/ai_assistant.py` | `/var/lib/asterisk/agi-bin/` | основной скрипт звонка |
| `agi/ai_assistant_last_will.py` | `/var/lib/asterisk/agi-bin/` | скрипт последней воли |
| `proto/speech_pb2.py`, `proto/speech_pb2_grpc.py` | `/var/lib/asterisk/agi-bin/` | заглушки gRPC |
| `sounds/service_unavailable.wav` | `/var/lib/asterisk/sounds/ai_bot/` | «Минуту, перевожу ваш звонок на специалиста» на случай отказа сервиса; имя зашито в скрипте |
| каталог `/var/lib/asterisk/sounds/ai_bot/cache` | | сюда скрипт складывает скачанные фразы |

Asterisk на этой станции работает под `root`, пользователя `asterisk` нет: владельца каталогов менять не нужно.

## 2. Выкладка скриптов

Только скриптом, руками через `scp` не копировать:

```powershell
.\tools\deploy_agi.ps1 -PwFile <файл с паролем станции> -DryRun
.\tools\deploy_agi.ps1 -PwFile <файл с паролем станции>
```

Он трогает только два наших AGI-файла и делает то, на чём уже теряли звонки:

- проверяет синтаксис под Python 3.9 (на станции 3.9.2, локально 3.12; запись `X | Y` в подписях функций
  валит скрипт при импорте);
- отвергает файлы с CRLF: такой shebang сбрасывает звонок без единой строки в логе сервиса;
- делает бэкап с отметкой времени, копирует во временное имя, компилирует питоном станции и подменяет одним
  переименованием;
- проверяет права 755. Потерянный бит исполнения выглядит как `Failed to execute ...: Permission denied` в
  `/var/log/asterisk/full`, а в обращении как «событие не дошло».

Классический астербот (`recosintsite_V2.py`, `agi_last_will.py`) и общий конфиг скрипт не касается: через них
идут живые звонки второго проекта.

### Заглушки gRPC

На станции стоят `grpcio 1.51.1` и `protobuf 4.21.12`, на сервисе новее. Заглушки в `ai_assistant/proto/`
собраны генератором `grpcio-tools==1.62.3` и импортируются с обеих сторон. Пересобирать генератором
**не новее 1.62.x**: с 1.64 в код добавляется обращение к `runtime_version`, которого на станции нет, и скрипт
не импортируется вовсе (абонент слышит тишину и отбой, аварийный перевод не спасает). Пакеты на самой станции
не понижать. Проверка после замены заглушек, на станции:

```bash
python3 -c "
import sys
sys.path.insert(0, '/var/lib/asterisk/agi-bin')
import grpc, requests, asterisk.agi, func_timeout, speech_pb2, speech_pb2_grpc, google.protobuf
print('grpc:', grpc.__version__, 'protobuf:', google.protobuf.__version__, 'IMPORT OK')
"
```

## 3. Диалплан

Наш контекст в `/etc/asterisk/extensions.conf`:

```
[pstn-ai]
exten => _X.,1,Answer
same => n,Set(CDR(userfield)=aitest)
same => n,Set(MIXMONITOR_FILENAME=/var/spool/asterisk/monitor/${UNIQUEID})
same => n,MixMonitor(${MIXMONITOR_FILENAME}.wav,W(2))
same => n,Verbose(======== BOT AI PROTOTYPE === с номера: ${CALLERID(num)})
same => n,Set(SpeechServiceHost=10.20.0.10)
same => n,Set(Aster2ServiceAddress=10.20.0.12:3511/Aster2ServiceWebHttp)
same => n,Set(AGIEXITONHANGUP=no)
same => n,EAGI(ai_assistant.py,120)
same => n,Verbose(======== BOT AI PROTOTYPE FINISHED ========)
same => n,Hangup()

exten => bot-lastwill,1,AGI(ai_assistant_last_will.py)
same => n,Return()
```

Что здесь неочевидно:

- **`Set(AGIEXITONHANGUP=no)` обязателен.** Со значением `yes` обрыв звонка оставляет дочерний процесс без
  `waitpid`, зомби копятся и роняют Asterisk целиком. На этой станции так уже падало.
- **Число `120` в `EAGI(...)` ничего не значит**: скрипт аргументы не читает. Предел звонка задан константой
  `CALL_TIMEOUT_S` в самом скрипте.
- **Расширения `h` нет, и добавлять его нельзя.** После перевода бот делает `Goto` в общий контекст, и `h`
  исходного контекста там не срабатывает: у переведённых звонков не было ни длительности, ни причины отказа.
  С 09.11.2026 скрипт сам вешает обработчик завершения на канал:
  `Set(CHANNEL(hangup_handler_push)=pstn-ai,bot-lastwill,1)`. Адрес зашит константой `LAST_WILL_TARGET`,
  переопределяется переменной канала `BotLastWillTarget`. Если вернуть `h`, об одном обрыве ERP узнает дважды.
- `Return()` в `bot-lastwill` обязателен: обработчик завершения вызывается как `Gosub`.
- `Aster2ServiceAddress`: служба, через которую оба скрипта ходят в ERP. Адрес снят с боевого лога станции
  (`grep -h "CURL JSON запрос к ERP" /var/log/asterisk/full* | tail -3`), этим же способом его перепроверять.
  Запасному значению в `recosintsite_V2.py` и конфигам службы в репозитории не верить, там другие адреса.
- Порты сервиса скрипт берёт по умолчанию. Если их меняли, добавить `Set(SpeechServiceHttpPort=...)` и
  `Set(SpeechServiceGrpcPort=...)`.

### Как править диалплан

Файл общий, `dialplan reload` перечитывает его целиком, на станции идут живые звонки второго проекта.

```bash
cp -p /etc/asterisk/extensions.conf /etc/asterisk/extensions.conf.bak_$(date +%Y%m%d_%H%M%S)
asterisk -rx "dialplan show" | grep -c "Context"      # число контекстов ДО правки
# правка
asterisk -rx "dialplan reload"
asterisk -rx "dialplan show pstn-ai"                   # должны быть и _X., и bot-lastwill
asterisk -rx "dialplan show" | grep -c "Context"      # то же число, что до правки
```

**Не добавлять приоритет в середину существующего расширения при живых каналах**: перечитывание сдвигает
приоритеты у выполняющегося звонка. Только новые расширения. Поэтому 09.11.2026 адрес подпрограммы прошит в
скрипте, а не задан строкой `Set` в потоке звонка.

Откат: вернуть бэкап тем же `cp -p` и сделать `dialplan reload`. Бэкап от 09.11.2026:
`extensions.conf.bak_20261109_133506`.

## 4. Скрипт последней воли и уход в ПЦК

Основной скрипт при обрыве канала умирает мгновенно (`SIGHUP` переведён на `SIG_DFL`, намеренно, против
зомби), поэтому сказать об обрыве не может. Это делает отдельный скрипт, которому не нужны ни grpc, ни
заглушки. Всё нужное основной скрипт заранее кладёт в переменные канала: `documentId`, `ScriptFinished`,
`LastRecognizedText`, `AiFailureReason`, `LastWrongGuess`, `conversation_start_time`.

- Событие завершения (`AiAssistantHangup`) уходит в ERP на каждом звонке, включая переведённые. По нему
  ставится длительность разговора. Не уходит только когда в канале нет ни кода обращения, ни идентификатора
  канала (строка `LAST WILL: сообщать не о чем`).
- Пока ERP отвечает отказом, сообщение повторяется до трёх раз с паузой: отказ означает «обращение ещё не
  зафиксировано» (клиент сбросил в первые секунды). Успешный ответ не повторяется.
- **В ПЦК («Перезвонить целевому клиенту») обращение уводит не обрыв, а причина** (`failureReason`).
  Обратный звонок положен только тому, кто остался без ответа по нашей вине. Пустая причина: «Клиент положил
  трубку сам», подтип не меняется.

| Что случилось | Текст причины в истории обращения |
|---|---|
| Сервис не ответил или оборвался поток распознавания (`failover_to_support`) | `отказал речевой сервис` |
| Необработанное исключение в скрипте (строка `FATAL` в логе станции) | `ошибка в скрипте` |
| Разговор упёрся в `CALL_TIMEOUT_S` | `превышена длительность разговора` |
| Не удалось скачать и проиграть фразу (строка `TTS ERROR`) | `не удалось озвучить ответ` |

Последняя причина снимается, как только следующая фраза ушла в трубку. Момент выставления причины виден в
логе станции строкой `FAILURE REASON: <текст>`.

## 5. Переключатели в скрипте

Обе константы лежат в `agi/ai_assistant.py`; после правки нужна выкладка, перезапуск сервиса не нужен.

- **`REAL_REDIRECT`** (с 19.08.2026 `True`): звонки действительно уходят на операторов командой
  `Goto pstn-out,<номер>,1`. Номер берётся из телефонного направления (поле «Телефон для заявок с сайта»);
  если такого номера в `pstn-out` нет, клиент услышит тишину и отбой. При `False` скрипт пишет в лог
  `REDIRECT (dry-run, ...)` и завершает разговор сам.
- **`ERP_INTEGRATION`** (`True`): на каждом звонке скрипт заводит обращение (`AiAssistantCallStart`), сообщает
  тему (`AiAssistantEquipment`), перевод (`AiAssistantTransfer`) и неузнанный вопрос (`AiAssistantUnknown`).
  Обращение создаётся в момент приёма звонка, а не при переводе: трубку бросают и на первой секунде.

Неузнанный вопрос уходит в ERP, только когда клиент произнёс осмысленную фразу, а записи под неё не нашлось.
По молчанию, пустому распознаванию и аварийному переводу он не отправляется. Промах называет сам сервис
(ключ `UnknownQuestion` в ответе `/dialog`).

Ни один вызов ERP не задерживает и не роняет разговор: таймаут пять секунд, ошибка уходит в лог станции
строкой `ERP ERROR ...`, звонок продолжается.

## 6. Как у оператора открывается карточка обращения (UL-18819)

Карточка открывается **по имени звонящего**, а не по номеру и не по коду обращения в канале.

1. ERP (обработчик 15422, `AiAssistantCallStart`) возвращает рядом с `documentId` строку `callerIdName` вида
   `<константа подмены>\t\tDOC<код обращения>`.
2. Скрипт перед каждым переводом ставит её в канал как есть: `Set(CALLERID(name)=<строка>)`. `Set` идёт до
   `Goto` и в том же захвате `_agi_lock`, на обоих путях перевода: обычном и аварийном.
3. Клиент оператора (`WorkForm.cs`) вырезает константу, проверяет `StartsWith("DOC")` и открывает документ.

Номер звонящего (`CALLERID(num)`) не подменяется: там настоящий телефон клиента. Имя не пришло, значит оно
просто не ставится, перевод идёт как обычно.

Разбор «карточка не открылась»: в логе станции должны быть подряд `Set(CALLERID(name)=...)` и
`Goto pstn-out,...`. Нет `Set`: ERP не вернула `callerIdName`. `Set` есть, а карточки нет: расходятся
константы подмены в ERP и в клиенте оператора.

## 7. Сеть

Со станции:

```bash
curl -s -m 5 http://10.20.0.10:8080/health && echo OK
timeout 3 bash -c "echo > /dev/tcp/10.20.0.10/50051" && echo "gRPC открыт"
timeout 3 bash -c "echo > /dev/tcp/10.20.0.12/3511" && echo "служба ERP на месте"
```

`nc` на станции нет, поэтому порты проверяются через `/dev/tcp`. Если сервис не отвечает, на его машине
открыть порты:

```powershell
New-NetFirewallRule -DisplayName "AIA speech HTTP" -Direction Inbound -LocalPort 8080 -Protocol TCP -Action Allow
New-NetFirewallRule -DisplayName "AIA speech gRPC" -Direction Inbound -LocalPort 50051 -Protocol TCP -Action Allow
```

Если закрыта служба ERP, звонок состоится, но обращения не будет: в логе станции `ERP ERROR ...`.

## 8. Контрольный звонок и что смотреть в логе

Живой лог: `asterisk -rvvv` или `/var/log/asterisk/full`. Строки по порядку:

- `=== AI ASSISTANT START <uniqueid> ===`: скрипт запустился;
- `LAST WILL HANDLER: pstn-ai,bot-lastwill,1`: обработчик завершения повешен на канал;
- `ERP: обращение <код> создано`. Если `не создано`, чаще всего на телефоне линии нет галочки
  «Виртуальный AI помощник»;
- `LISTEN ON`: глухота на время фразы бота снята, скрипт слушает;
- `FINAL: <текст>`: что распознано на реплике;
- `REDIRECT -> <номер>`: бот довёл разговор до перевода;
- `FAILURE REASON: <текст>`: названа причина, по которой обращение уйдёт в ПЦК;
- `=== AI ASSISTANT LAST WILL <uniqueid> ... ===`: сработала последняя воля, ровно один раз, в том числе
  после перевода.

В ERP: обращение создано в подтипе 3831 «АстерБот AI: Новое обращение», в истории вопрос клиента и тип
оборудования, у звонка заполнена длительность. Сброс до перевода подтип на ПЦК не меняет.

Если бот молчит:

1. Сервис поднят и отвечает `/health`.
2. Скрипты на месте и с правами 755: `ls -la /var/lib/asterisk/agi-bin/`.
3. Бот сразу играет «Минуту, перевожу ваш звонок на специалиста» и переводит: это аварийный переход,
   сервис не отвечал в момент звонка. Смотреть `logs/aia.log` на машине сервиса.

Тайминги по реплике: `curl -s http://10.20.0.10:8080/metrics`. Отрезки `speech_end→stt_done` и
`stt_done→dialog_done` есть там; скачивание и начало проигрывания фразы видны только в логе станции метками
`TIMING download_start`, `TIMING download_done`, `TIMING playback_start`, и только при промахе кэша станции.

## 9. Голос, кэш станции и группы линий

- Имя файла фразы на станции считается от текста и подписи звука (модель синтеза, голос, версия обработки,
  отпечаток библиотеки записей). Смена голоса или записи меняет имена, станция скачивает новые сама. Чистить
  кэш руками не нужно; старые файлы можно убрать ради места:
  `rm -f /var/lib/asterisk/sounds/ai_bot/cache/*.wav`.
- У каждой группы линий свои служебные фразы и голос. Обработчик 15424 присылает их массивом `line_groups`,
  сервис выбирает набор по набранному номеру (`dialedNumber`), сравнивая последние десять цифр. Номер, не
  найденный ни в одной группе, получает общий набор. База знаний общая.
- Если в группе включено «использовать записанные аудиофайлы» и у фразы заполнен путь, сервис отвечает самим
  путём с признаком `FileIsOnStation=True`, и скрипт ничего не скачивает. Такие файлы обязаны лежать на
  станции под `/var/lib/asterisk/sounds`: сервис их не отдаёт и проверить не может.
