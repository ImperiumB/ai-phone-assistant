# UL-17568 — Виртуальный AI помощник: прототип речевого контура

**Дата:** 13.08.2026
**Тикет:** [UL-17568](http://jira.example.com:8080/browse/UL-17568) «Виртуальный AI помощник», тип «Проект», приоритет Критичный
**Этап:** 1 из 6 — прототип речи. Остальные пять перечислены в разделе 11.

---

## 1. Зачем это

UL-17568 требует бота, который принимает входящий звонок, распознаёт свободную речь клиента, ищет похожий по смыслу вопрос в базе знаний и по сценарию переводит звонок в нужный отдел. Сейчас распознавание и синтез покупаются у Яндекса. Требование — перейти на собственные модели, без оплаты за минуты.

Прежде чем строить справочники, формы и обработчики в ERP, нужно ответить на вопрос, от которого зависит жизнеспособность всего проекта:

> **Достаточно ли хороши и достаточно ли быстры свободные модели на нашем телефонном канале, чтобы заменить Яндекс?**

Прототип отвечает на этот вопрос живым звонком и цифрами. Ничего больше он не делает.

## 2. Границы

**Входит:**
- Новый AGI-скрипт на Астериске для входящего номера `74951468847`
- Правка extension `74951468847` в `extensions.conf`: добавить `MixMonitor` и заменить `Background(ai_bot/labubu)` на вызов нашего скрипта
- Speech-сервис (демон) с VAD, распознаванием, синтезом и поиском по базе знаний
- **Не менее двух сменных движков распознавания** для сравнения на одном материале
- Плоская база знаний в JSON на 10–20 записей
- Заглушка диалоговой логики, повторяющая контракт ERP
- Замер задержки, качества и нагрузки

**Не входит — сознательно:**
- Любые изменения в ERP: справочники, формы, обработчики, подтипы обращений
- Правки обработчика 13161 и боевого `recosintsite_V2.py`
- Изменения боевых входящих номеров (`74951377014` и прочие) и контекста `pstn-out`. Трогаем **только** тестовый `74951468847`
- Создание обращений, запись в БД
- Обработка обрывов в ПЦК, сценарии переводов по ТО
- **Окончательный выбор модели.** Прототип сравнивает кандидатов и даёт цифры; решение принимается после, с учётом ответа по GPU

## 3. Исходные данные

### Железо (замер 13.08.2026)

| | Астериск | Виртуалка разработчика |
|---|---|---|
| CPU | 24 ядра Xeon E5-2670 v3 | 10 ядер Xeon E5-2690 v3 |
| RAM | 7,7 ГБ | 25 ГБ |
| GPU | нет | нет |
| Python | 3.9.2 | 3.12 |
| Адрес | — | `10.20.0.10` |

У Астериска мало памяти, и грузить его нельзя в принципе — он держит живые звонки, просадка CPU даст заикания в трубке.

**Сервер с GPU в компании есть** (подтверждено 13.08.2026), но прототип сознательно начинается на CPU: так быстрее стартовать и ни с кем не согласовывать. Переезд на GPU — запасной ход, если замеры покажут неприемлемую задержку. Характеристики GPU-сервера уточнить перед переездом.

Отсюда следует требование к коду: **всё, что зависит от устройства вычислений, изолировано за интерфейсом движка** (см. 5.2). Переезд на GPU должен быть сменой параметра конфига, а не переписыванием.

### Что уже работает

Входящий номер **`74951468847`** («BOT AI: labubu», контекст `pstn-in`, `extensions.conf:41-46`) — отвечает, проигрывает `ai_bot/labubu`, кладёт трубку. Проверен живым звонком 13.08.2026. Это наша песочница.

Для сравнения, боевой входящий `74951377014` пишет разговор через `MixMonitor` в `/var/spool/asterisk/monitor/${UNIQUEID}.wav49` и уходит в `Queue(60001,tT,,,50,)`.

### Что переиспользуем из существующего решения

Схема «тонкий AGI-клиент + логика на сервере» из `recosintsite_V2.py` правильная и не пересматривается. Контракт ответа логики:

| Поле | Значение |
|---|---|
| `Action` | `Recognize` — продолжаем слушать; `Redirect` — переводим; `Hangup` — кладём трубку |
| `TextToSpeak` | что озвучить |
| `FileToPlayback` | имя файла кэша для этой фразы |
| `RedirectExten` | куда переводить при `Redirect` |
| `ConversationPoint` | текущая точка диалога |

Все выстраданные правки скрипта переносятся дословно: `RLock` вокруг всех `agi.*`, `daemon=True` для потоков синтеза, `os._exit()` вместо `sys.exit()` в фатальном обработчике, `Playback` для синхронной озвучки против `background` для асинхронной, атомарная запись WAV-кэша через `.tmp` + `os.replace()`, проверка заголовка WAV перед проигрыванием.

### Почему сервис отдельным демоном

Каждый звонок в Asterisk — отдельный процесс AGI-скрипта. Загружать в него нейросеть невозможно: старт занял бы десятки секунд и гигабайты памяти на каждый звонок. Демон грузит модели один раз при запуске и обслуживает все звонки.

Побочная выгода: сеть до сервиса локальная вместо интернета до Яндекса, поэтому ретрай при обрыве потока распознавания становится дешёвым. Сейчас любой транзиентный обрыв убивает звонок целиком.

## 5. Компоненты

### 5.1 `ai_assistant.py` — AGI-клиент

**Назначение:** мост между каналом Asterisk и speech-сервисом. Логики не содержит.

**Зависимости:** `pyst2`, `grpcio`, `requests`, `pydub`, `func_timeout` — **всё уже установлено** на Астериске, ставить нечего. Python 3.9 — синтаксис новее не использовать.

Транспорт выбран gRPC, а не WebSocket, по двум причинам: `websockets` на Астериске нет, а pip там версии 20.3.4 и тянуть в боевой сервер новые пакеты не хочется; `grpcio` же уже стоит и годами гоняет поток в Яндекс. Плюс код двунаправленного потока уже написан и отлажен в `recosintsite_V2.py` — генератор `recognize_stt()` отдаёт куски, цикл `for r in it:` читает события. Мы переиспользуем структуру, меняя только адрес и `.proto`.

**Что делает:**
1. Читает переменные канала, открывает gRPC-поток к сервису
2. Читает аудио с дескриптора 3 кусками по 8000 байт, отдаёт генератором в поток
3. Принимает события распознавания, на финальном — дёргает диалоговую логику
4. Получает `Action`, озвучивает `TextToSpeak`, выполняет действие
5. По `Redirect` — `Goto`, по `Hangup` — кладёт трубку

**Ограничение по времени:** `func_timeout` на весь разговор, как сейчас. Дедлайн gRPC-потока — трёхкратный от него, чтобы осиротевший поток не висел вечно (эта защита уже есть в боевом скрипте, переносим).

### 5.2 Speech-сервис

Один процесс, три ручки.

#### gRPC `Recognize` — распознавание

Двунаправленный поток. Клиент шлёт сообщения с сырым PCM, сервис отвечает событиями:

```
StreamRequest  { bytes audio_chunk }
StreamResponse { enum type = PARTIAL | FINAL | SILENCE; string text; int32 silence_ms }
```

Типы событий намеренно повторяют яндексовые `partial` / `final`, чтобы логика ветвления в скрипте осталась прежней.

Внутри: буфер → Silero VAD определяет границы реплики → апсемплинг 8→16 кГц (модели распознавания работают на 16 кГц) → модель → событие.

VAD заменяет EOU-классификатор Яндекса. Параметр паузы, после которой реплика считается законченной, выносится в конфиг — сейчас у Яндекса это 3000 мс.

**Движки распознавания сменные.** За общим интерфейсом (`transcribe(pcm16k) -> str`) стоит несколько реализаций, движок выбирается параметром конфига. Кандидаты:

| Движок | Чем интересен | Чем рискован |
|---|---|---|
| **Vosk** (ru) | Настоящий стриминг, работает на CPU, лёгкий | Точность заметно ниже остальных |
| **GigaAM v2** (Сбер, MIT) | Лучший WER на русском среди открытых | Стриминга нет — нужно скользящее окно поверх VAD |
| **Whisper large-v3-turbo** (через faster-whisper) | Проще всего запустить, много обвязок | На телефонной тишине склонен выдумывать несуществующие фразы |
| **NeMo FastConformer** (NVIDIA, ru) | Настоящий cache-aware стриминг, ближе всего к поведению Яндекса | Тяжелее в настройке, на CPU может не успевать |

Обязательны к прогону **Vosk и GigaAM** — они закрывают крайние точки размена «быстро, но грубо» против «точно, но медленно». Остальные — если останется время.

#### `POST /dialog` — логика диалога

**Формат запроса и ответа повторяет `ReturnConversationIntermediateResult3` один в один** — список пар `Key`/`Value`. Это сделано намеренно: когда логика переедет в ERP, в скрипте меняется только адрес.

В прототипе внутри: эмбеддинг реплики → косинусная близость со всеми вопросами базы знаний → если максимум выше порога, отдаём уточняющий вопрос записи; иначе — фразу про перевод и `Action=Redirect`.

Порог близости выносится в конфиг и подбирается на живых звонках. Это главный настроечный параметр прототипа.

#### `GET /tts` — синтез

Параметры: текст и голос. Отдаёт **WAV PCM 16 бит, моно, 8000 Гц** — ровно то, что умеет играть `format_wav` в Asterisk. Синтезированное кэшируется на диске сервиса по хешу текста и голоса, повторные фразы отдаются мгновенно.

Клиент кладёт полученный файл в `/var/lib/asterisk/sounds/ai_bot/cache/` и проигрывает. Перед проигрыванием прогоняет `check_wav_header()` — функция уже написана, ловит битые файлы, из-за которых клиент слышит тишину.

### 5.3 База знаний

JSON рядом с сервисом. Поля повторяют будущий справочник из ТЗ, чтобы перенос был механическим:

```json
{
  "id": 1,
  "question": "стиральная машина не отжимает",
  "clarifying_question": "Правильно я понял, что вас интересует ремонт стиральной машины? Ответьте, пожалуйста, да или нет",
  "positive_answers": ["да", "верно", "точно", "именно"],

  "equipment_type": "Стиральные машины"

```

Эмбеддинги вопросов считаются один раз при старте сервиса.

## 6. Сценарий звонка

Реализуется Пример 1 из ТЗ целиком:

1. Клиент звонит на `74951468847`, Asterisk отвечает и начинает запись
2. Бот: «Здравствуйте, чем могу помочь?»
3. Клиент: «Стиральная машина не отжимает»
4. Ищем в базе знаний. Нашли — бот: «Правильно я понял, что вас интересует ремонт стиральной машины?»
5. Клиент: «Да» → бот: «Соединяю вас с отделом продаж» → кладёт трубку с пометкой в логе, куда бы перевёл

**Ветки:**
- Не нашли в базе → фраза про перевод, звонок завершается, вопрос дописывается в JSON
- Ответ распознан как отрицательный → «Попробуйте переформулировать вопрос», возврат к шагу 3
- Тишина дольше порога → фраза при тишине; если тишина повторилась — завершение

Реального перевода в очередь в прототипе нет — только запись в лог. Иначе мы дёрнем живых операторов.

## 7. Обработка ошибок

| Что случилось | Поведение |
|---|---|
| Сервис недоступен при старте звонка | Озвучить фразу про перевод, завершить. Не «критическая ошибка» — клиент не должен это слышать |
| Обрыв gRPC-потока в середине | Один ретрай с переподключением, состояние диалога сохраняется. Не вышло — мягкое завершение. **Требует вынести `os.fdopen(3, 'rb')` наружу из генератора** — в боевом скрипте он открывается внутри и закрывается вместе с генератором, из-за чего ретрай сейчас невозможен |
| Модель не отдала результат за 10 секунд после конца реплики | Считаем, что распознать не удалось, идём по ветке тишины. Значение в конфиге |
| Битый или отсутствующий WAV | Лог с явным текстом, что клиент услышит тишину |
| Любое необработанное исключение | Лог, `os._exit(1)`. Отчёт по каналу пишет `agi_last_will.py` |

Принцип: **клиент никогда не слышит слово «ошибка»**. Любой сбой выглядит как обычный перевод звонка.

## 8. Критерии успеха

Прототип считается успешным, если получены измеренные значения по трём пунктам — независимо от того, хорошие они или плохие. Отрицательный результат тоже результат: он экономит закупку железа.

Все три пункта замеряются **по каждому движку распознавания отдельно**, результат сводится в одну таблицу.

1. **Задержка** от конца фразы клиента до начала ответа бота. Замеряется по меткам на каждом этапе: конец речи по VAD → распознано → логика ответила → синтез готов → началось проигрывание. Разбивка по этапам обязательна — иначе непонятно, что именно тормозит. Ориентир Яндекса — около секунды
2. **Качество распознавания.** Расшифровки сверяются с записями `MixMonitor` вручную. Отдельно фиксируются случаи, когда ошибка увела диалог не в ту ветку — это важнее сырого процента ошибок, потому что «отжимает» вместо «отжимало» безобидно, а «стиральная» вместо «посудомоечная» ломает сценарий
3. **Нагрузка CPU и память на один звонок** → расчёт, сколько параллельных звонков потянет машина

Цифры по первому и третьему пунктам — основание для разговора о закупке GPU.

## 9. Риски

| Риск | Насколько вероятен | Что делаем |
|---|---|---|
| Задержка на CPU неприемлема для живого разговора | **Высоко** — это ожидаемый исход, а не неожиданность | Переезжаем на существующий GPU-сервер. Риск снят наличием железа: вопрос в сроках переезда, а не в бюджете |
| Качество распознавания на 8 кГц заметно ниже Яндекса | Средне | Сравниваем несколько моделей на одном материале |
| Порог близости не разделяет вопросы: ложные срабатывания либо ничего не находится | Средне | Порог в конфиге, подбирается на живых звонках. Если не разделяется — второй эшелон в виде Gemma 3n как реранкера |
| Python 3.9 на Астериске мешает библиотекам | Снято | Все нужные пакеты уже стоят, новых не ставим |
| Сеть между Астериском и виртуалкой даёт задержку | Низко | Одна подсеть `192.168.111.x`. Замерить `ping` до старта |
| Нагрузка от прототипа мешает боевым звонкам | Низко | Модели на отдельной машине, на Астериске только тонкий клиент |

## 10. Открытые вопросы

- **GPU-сервер: что именно за железо.** Наличие подтверждено, характеристики неизвестны. Нужны модель карты и объём видеопамяти — от этого зависит, какие движки туда влезут. Выяснить до переезда, но не раньше: на выбор для CPU-этапа это не влияет
- **Маршрутизация по чекбоксу.** Диалплан прописан по номерам вручную (`Queue(60001)` захардкожен). Чекбокс «Виртуальный AI помощник» сам по себе на маршрут не повлияет. Нужно либо генерить диалплан из ERP, либо спрашивать ERP в начале входящего. Решается на этапе 2
- **Голоса.** ТЗ требует расширить выбор и найти менее роботизированные. В прототипе берём один голос Silero V5, выбор откладываем. В комментариях к тикету Гарасика уже приложил сэмплы Silero V5, Sber SaluteSpeech, МТС Exolve и других — использовать как отправную точку
