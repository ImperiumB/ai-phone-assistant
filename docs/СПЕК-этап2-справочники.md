# UL-17568 — этап 2: справочники в ERP и доставка данных в сервис

**Дата:** 14.08.2026
**Тикет:** [UL-17568](http://jira.example.com:8080/browse/UL-17568)
**Этап:** 2 из 6. Предыдущий — `СПЕК-прототип-речи.md` (закрыт, бот работает на живых звонках).

---

## 1. Зачем

Сейчас база знаний бота — файл JSON рядом с сервисом. Чтобы добавить тему или поправить формулировку, нужен программист. Это тормозит всё: за два дня работы прототипа база менялась пять раз, и каждый раз через правку файла.

Задача этапа — перенести содержимое в справочники ERP, чтобы его вели люди, а не разработчик.

**Поведение бота при этом не меняется.** Он будет делать ровно то же самое, теми же моделями и с той же скоростью. Это шаг не по функциям, а по управляемости.

## 2. Границы

**Входит:**

- три новых справочника: база знаний, формулировки, сценарии;
- новые поля в «Телефонах Линии» и «Группах линий»;
- SQL для создания таблиц и колонок;
- формы списка и карточки для новых справочников;
- обработчик, который собирает всё содержимое и отправляет его в сервис;
- приёмная ручка в сервисе, копия данных на диске, возраст данных в проверке живости;
- перенос нынешнего содержимого (28 записей, 348 формулировок) в справочники.

**Не входит:**

- обращения: новый подтип, создание при звонке, тип оборудования в обращении, обрывы в ПЦК — это этап 3;
- переезд логики диалога из `dialog.py` в обработчик — это этап 4;
- маршрутизация звонков по чекбоксу «Виртуальный AI помощник» — этап 6;
- пересборка Aster2Service. Служба обслуживает все живые звонки боевого астербота, трогать её ради справочника — плохой размен.

## 3. Разделение труда

Доступ к базе у меня **только на чтение**, а обработчики, роботы и подтипы создаются в самой системе.

| Кто | Что делает |
|---|---|
| **Я** | Метаданные, SQL-скрипты, формы, код обработчика, код приёмной ручки сервиса, перенос содержимого |
| **заказчик** | Создаёт заготовки обработчика и робота и называет их номера; создаёт ключ доступа; выполняет SQL; заливает собранное |

Номера обработчика, робота и ключа доступа проставляются в код после того, как они созданы.

## 5. SQL

Выполняет заказчик. Скрипты пишутся отдельными файлами в `sql/`, каждый идемпотентен: повторный запуск не ломается.

1. `01_ai_scenarios.sql` — таблица, последовательность, первичный ключ
2. `02_ai_knowledge_base.sql` — то же, плюс внешний ключ на сценарии
3. `03_ai_kb_phrases.sql` — то же, плюс внешний ключ на базу знаний и индекс по `KNOWLEDGE_BASE_ID`
4. `04_line_phones_ai.sql` — колонка `IS_AI_ASSISTANT`
5. `05_line_groups_ai.sql` — четырнадцать колонок блока настроек

Индекс по `KNOWLEDGE_BASE_ID` обязателен: обработчик собирает формулировки выборкой по записи.

## 6. Формы

**Список базы знаний.** Колонки: вопрос, сценарий, тип оборудования, признак «добавлено ботом», признак «не активна». Фильтр по признаку «добавлено ботом» — через него человек разбирает то, что бот накопил.

Числа формулировок в списке нет намеренно: подсчёт по связанной таблице для каждой строки — это либо вычисляемое поле с подзапросом, либо лишний запрос на отрисовку списка. Ради колонки, которую видно и в карточке, платить этим не стоит.

**Карточка базы знаний.** Сверху поля записи, снизу табличка формулировок с возможностью добавлять и удалять строки. Плюс кнопка «Отправить в сервис» — вызывает тот же обработчик, что и робот, чтобы поправил и сразу проверил звонком.

**Список и карточка сценариев.** Простые: название, тип действия, направление.

Отдельных форм для формулировок не делаем — они правятся только внутри карточки базы знаний.

## 7. Доставка данных в сервис

### 7.1 Схема

```
Обработчик «Отправить базу знаний AI-помощника»
   │  собирает справочники, складывает в JSON
   ▼
POST http://10.20.0.10:8080/knowledge
   │
   ▼
Сервис: проверил, пересчитал эмбеддинги, сохранил копию на диск
```

Обработчик вызывается двумя способами: роботом по расписанию раз в десять минут и кнопкой с формы справочника.

**Почему ERP толкает, а не сервис забирает.** Забирать архитектурно чище, но для этого нужна новая точка входа в Aster2Service, а через неё идут все живые звонки боевого астербота. Пересборка и переустановка этой службы ради справочника — риск, несоразмерный задаче.

### 7.2 Формат посылки

```json
{
  "generated_at": "2026-08-14T15:00:00",
  "settings": {
    "line_group_id": 1,
    "voice": "eugene",
    "greeting": "Здравствуйте, чем могу помочь?",
    "misrecognition": "Попробуйте переформулировать свой вопрос, пожалуйста",
    "transfer": "Минуту, перевожу ваш звонок на специалиста",
    "silence": "Вы меня слышите?",
    "wrong_guess": "Тогда подскажите, пожалуйста, что вас интересует?",
    "positive_answers": ["да", "так", "ага"],
    "negative_answers": ["нет", "не то"],
    "use_recorded_audio": false,
    "paths": {"greeting": "", "misrecognition": "", "transfer": "", "silence": "", "wrong_guess": ""}
  },
  "records": [
    {
      "id": 1,
      "question": "стиральная машина не отжимает",
      "phrases": ["стиралка машинка сломалась", "стиралка потекла"],
      "clarifying_question": "Правильно я понял, что вас интересует ремонт стиральной машины? Ответьте, пожалуйста, да или нет",
      "positive_reply": "Соединяю вас со специалистом по ремонту стиральных машин, оставайтесь на линии",
      "equipment_type_id": 12,
      "equipment_type": "Стиральные машины",
      "scenario_id": 1,
      "telephone_direction_id": 53,
      "redirect_exten": "7105"
    }
  ]
}
```

Записи с пустым `clarifying_question` и записи с `NOT_ACTIVE = 1` в посылку не попадают — фильтрует обработчик.

### 7.3 Настройки: одна группа линий на этом этапе

Сервис принимает настройки **одной** группы линий — той, которой принадлежит телефон линии с проставленным чекбоксом. Если таких групп окажется несколько, обработчик берёт первую по коду и пишет предупреждение в лог.

Это осознанное упрощение. Выбор настроек под конкретный звонок требует, чтобы телефонный скрипт передавал набранный номер, а сервис знал соответствие номеров группам. Всё это естественно появится на этапе 4, когда логика диалога переедет в обработчик и будет получать контекст звонка целиком. Городить это сейчас — работа, которую придётся выбросить.

### 7.4 Приёмная ручка сервиса

`POST /knowledge`

- Проверяет структуру. Кривая посылка отвергается целиком с кодом 400 и внятным сообщением — **частично применять нельзя**, иначе база окажется в промежуточном состоянии.
- Пересчитывает эмбеддинги. На 348 формулировках это секунды.
- Сохраняет посылку на диск.
- Возвращает: сколько записей и формулировок принято.

**Пока пересчёт идёт, звонки обслуживаются старым индексом.** Подмена — одной операцией в конце, когда новый индекс готов целиком.

`GET /health` дополняется возрастом данных: когда пришла последняя посылка и сколько в ней записей. Если робот сломается, это будет видно сразу.

**Что чем перекрывается.** Присланные настройки — голос и фразы — становятся действующими и перекрывают значения из файла запуска сервиса. Переменные `AIA_TTS_VOICE`, `AIA_KNOWLEDGE_PATH` после первой успешной посылки перестают влиять на что-либо; они остаются только как значения по умолчанию до её прихода. Настройки, которых нет в посылке — движок распознавания, модель синтеза, пауза тишины, порог близости, — по-прежнему берутся из файла запуска.

При старте сервис поднимает копию с диска. Ждать первой посылки нельзя: сервис перезапускается за минуту, а робот приходит раз в десять.

### 7.5 Чего не делаем

**Проверки подлинности на ручке нет.** Сеть внутренняя, сервис слушает только её. Отмечено как известный риск: кто угодно из локальной сети может подменить базу знаний бота. Если понадобится — закрывается общим ключом в заголовке, но городить это сейчас смысла нет.

## 8. Перенос содержимого

Нынешние 28 записей и 348 формулировок переносятся в справочники скриптом, который порождает `INSERT`-ы. Выполняет заказчик.

Сценарии создаются по одному на каждое телефонное направление, участвующее в базе.

**После переноса файл `knowledge_base.json` остаётся** как аварийная копия на случай, если ERP недоступна при первом запуске. Сервис использует его, только если на диске нет копии присланной посылки.

## 9. Ограничения платформы

- Имя колонки в метаданных — **не длиннее 28 символов**, имя таблицы — **не длиннее 26**. Все имена выше проверены.
- Обработчики: .NET 4.8, LangVersion 7.3. Никаких конструкций новее.
- Обработчики свободно используют `HttpClient` — подтверждено, так работает 12801 с API hh.ru.
- Каждый справочник обязан иметь `<property id="ID" type="System.Int64" required="true"/>`.
- Свободные dbid начинаются с 56443: максимальный занятый — 56442.

## 10. Критерии готовности

1. Справочники видны в интерфейсе, записи создаются и правятся руками.
2. Кнопка «Отправить в сервис» с формы доставляет данные: сервис отвечает числом принятых записей.
3. Робот доставляет то же самое по расписанию.
4. `GET /health` показывает возраст данных.
5. Правка формулировки в справочнике меняет поведение бота на следующем звонке — проверяется живым звонком.
6. Перезапуск сервиса не теряет данные: поднимается с диска.
7. Отключение робота на час не ломает бота — он работает на последней копии, а возраст данных виден в проверке живости.

Пункт 5 — главный. Остальное можно проверить в браузере, а его только звонком.

## 11. Открытые вопросы

- **Номера обработчика, робота и ключа доступа** — выделяет заказчик, проставляются в код после создания.
- **Порог близости** остаётся настройкой сервиса, а не справочника. Вынести его в интерфейс заманчиво, но неверная правка ломает бота молча: он либо начнёт отфутболивать нормальные вопросы, либо хватать посторонние. Пока порог меняется вместе с замером.
- **Направления без галочки «Доступен для перевода»** — сантехника, электрика, сушильные и швейные машины, Dyson, Xiaomi, Apple Watch. Пока справочник запрещает перевод, бот их не покроет. Решение за владельцем справочника.
